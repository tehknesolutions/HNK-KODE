# haKodan — KODINS Multilingual & Multi-Target Registry v1

**Base lexical:** VHK/HNK lexical shortlist v0.2 (127 entries).

## Status rule

- **CANON:** currently only AHNUVA, EMANU, HAYA, HODERU, KODAN.
- **PROVISIONAL:** the other 122 selected forms remain discovery candidates; they are useful as working Kodins but are not yet HNK lexical canon.

## Compiler principle

A Kodin is not translated by string substitution. Each surface token resolves to a language-neutral `Semantic ID`, which is lowered through AST → HOM → HNK-IR and then through a target adapter/backend.

```text
PT-BR / EN / HNK-KODE / MIX
           ↓
     Semantic IDs
           ↓
          AST
           ↓
          HOM
           ↓
        HNK-IR
           ↓
   ┌───────┼────────┬────────┬─────────┐
   ↓       ↓        ↓        ↓         ↓
 JS/TS   Python   C#/C++    Rust      WASM
                              ↓         ↓
                            LLVM IR   bytecode
                              ↓         ↓
                         Assembly / ISA
                              ↓
                    x86-64 / ARM64 / RISC-V
                              ↓
                         MACHINE CODE
```

High-level source generation and native-machine compilation are different backends of the same semantics. Native machine code is architecture-specific; there is no single universal machine binary.

## Backend rule

Para dizer que haKodan 'converte para qualquer linguagem', a formulação técnica correta é: **qualquer linguagem/ISA para a qual exista um backend/adapter validado**. O core permanece independente de target.

Targets recomendados por camadas:

1. **Source targets:** TypeScript/JavaScript, Python, C#, C++, Rust, PHP, Java/Kotlin, Swift.
2. **Portable low-level targets:** WebAssembly, LLVM IR, SPIR-V quando aplicável.
3. **VM/bytecode:** haKodan bytecode próprio, JVM bytecode, .NET IL quando adapters existirem.
4. **Native:** x86-64, ARM64, RISC-V via backend/LLVM ou assembler dedicado.
5. **Binary:** executáveis/objetos específicos de plataforma, como ELF, PE/COFF e Mach-O.

A reversão de código-máquina para VHK não é garantidamente lossless; por isso o haKodan deve preservar provenance/source maps do Semantic ID até offsets do binário.
